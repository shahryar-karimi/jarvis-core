# `jarvis-device.v1` WebSocket protocol

Status: frozen Core/Agent V1 transport contract.

This document is normative for the `jarvis-device.v1` WebSocket subprotocol.
The committed [machine-readable contract](jarvis-device-v1.contract.json)
contains the golden messages, closed message shapes, capability/action set, and
close-code registry exercised by the Core test suite.

The words **MUST**, **MUST NOT**, **SHOULD**, and **MAY** describe protocol
requirements. V1 is a closed protocol: adding, removing, renaming, or changing
the meaning or type of any envelope or payload field is a breaking change and
MUST use a new `jarvis-device.v2` subprotocol. Unknown fields are not an
extension mechanism and are rejected.

## Transport and authentication

- Default endpoint: `WS /api/v1/devices/ws` (the `/api/v1` prefix follows the
  Core deployment's `JARVIS_API_PREFIX` configuration)
- WebSocket subprotocol: exactly `jarvis-device.v1`
- Authentication: `Authorization: Bearer <device-token>` during the HTTP
  upgrade
- Frames: UTF-8 text containing one JSON object

JSON numbers MUST be finite; the non-standard `NaN`, `Infinity`, and
`-Infinity` constants are invalid.

Core authenticates the device before accepting the WebSocket. Device tokens
MUST NOT be placed in the URL; query-string credentials are ignored. The Agent
MUST store its token in an OS credential store or an ACL-restricted file and
MUST use WSS outside an explicitly trusted local development environment.

Core denies the HTTP upgrade with status `403` when gateway resources are
unavailable, the exact subprotocol was not offered, or the device credential is
missing, invalid, or already revoked. Because the WebSocket was never accepted,
these failures do not have a WebSocket close code. The identical status avoids
revealing which authentication or gateway precondition failed.

Binary frames are rejected with close code `1003`. Core measures text-frame
limits in UTF-8 bytes. The configured limit is announced in `server.hello`; an
oversized frame is rejected with `1009`.

## Common envelope

Every accepted JSON message has exactly these five fields:

| Field | Type | Rule |
| --- | --- | --- |
| `v` | integer | MUST equal `1` |
| `type` | string literal | MUST be one of the direction-specific types below |
| `message_id` | UUID string | Generated by the sender and unique within the connection |
| `session_id` | UUID string | MUST equal the value in Core's `server.hello` |
| `payload` | object | Closed shape selected by `type` |

Core rejects an Agent message with an unknown or extra envelope field, an
unknown or extra payload field, a mismatched session, or a replayed message ID.
Core remembers the most recent 1,024 Agent message IDs per connection. UUIDs
use their canonical hyphenated string form in emitted messages.

## Connection state machine

```text
HTTP upgrade + auth + subprotocol
              |
              v
        Core accepts socket
              |
              v
      Core -> server.hello
              |
       device.hello only
       (within 10 seconds)
              |
              v
      Core -> server.ready
              |
              v
            READY
  heartbeat / capability update /
  command execution and result
              |
              v
          DISCONNECTED
```

`device.hello` MUST be the first Agent message and MUST arrive within 10
seconds. Before `server.ready`, no other Agent message is valid. In READY,
`device.hello` is no longer valid. A protocol-shape or state error causes Core
to send `protocol.error` when a session exists, then close with `4400`.

## Agent-to-Core messages

### `device.hello`

Required first message:

```json
{
  "agent": "jarvis-agent",
  "version": "1.0.0",
  "platform": "windows",
  "capabilities": ["open_app", "files", "system"]
}
```

`agent`, `version`, and `platform` are non-empty descriptive strings, limited
to 80, 40, and 80 characters respectively. `capabilities` is a set of at most
32 known capability IDs. Core intersects this advertisement with the device's
owner-granted capabilities.

### `heartbeat.pong`

```json
{
  "nonce": "22222222-2222-4222-8222-222222222222"
}
```

The UUID MUST exactly echo the outstanding `heartbeat.ping` nonce. An absent,
late, duplicated, or unexpected nonce is invalid. A valid pong updates device
presence.

### `capabilities.update`

```json
{
  "capabilities": ["open_app"]
}
```

Replaces the Agent's advertised set for the current session. Core responds
with `capabilities.ack` containing the newly effective intersection. It does
not change the persistent owner grant.

### `command.result`

```json
{
  "command_id": "33333333-3333-4333-8333-333333333333",
  "succeeded": true,
  "output": {"opened": "PyCharm"},
  "error": null
}
```

`command_id` MUST identify a command pending for this exact device and session.
`output` and `error` are optional on the wire and default to `null`. The
resolved result obeys these invariants:

- When `succeeded` is `true`, `error` MUST be `null`.
- When `succeeded` is `false`, `error` MUST be a non-blank string of at most
  2,000 characters.
- `output` MAY be any JSON value whose complete message remains within the
  negotiated frame limit.

A well-formed result for an unknown, expired, already-resolved, or wrong-session
command does not disconnect the Agent. Core sends `command.result_rejected`.

## Core-to-Agent messages

### `server.hello`

```json
{
  "device_id": "aaaaaaaa-aaaa-4aaa-8aaa-aaaaaaaaaaaa",
  "heartbeat_interval_seconds": 30,
  "max_message_bytes": 65536
}
```

This is Core's first accepted-socket message. The envelope's `session_id`
establishes the session the Agent MUST echo. The positive heartbeat interval
may be an integer or JSON number; the maximum message size is a positive
integer.

### `server.ready`

```json
{
  "device_id": "aaaaaaaa-aaaa-4aaa-8aaa-aaaaaaaaaaaa",
  "effective_capabilities": ["open_app"]
}
```

Confirms the connection is ready. `effective_capabilities` is the intersection
of owner grants and the Agent advertisement. The Agent MUST execute only this
set and MUST still apply its own local policy.

### `heartbeat.ping`

```json
{
  "nonce": "22222222-2222-4222-8222-222222222222"
}
```

The Agent MUST answer with `heartbeat.pong` using the same nonce before Core's
heartbeat deadline, currently half of the advertised interval with a one-second
minimum.

### `capabilities.ack`

```json
{
  "effective_capabilities": ["open_app"]
}
```

Acknowledges a `capabilities.update` and replaces the session's effective set.

### `command.execute`

```json
{
  "command_id": "33333333-3333-4333-8333-333333333333",
  "capability": "open_app",
  "action": "open",
  "arguments": {"name": "PyCharm"},
  "issued_at": "2026-08-18T12:00:00+00:00",
  "deadline_at": "2026-08-18T12:00:30+00:00"
}
```

Timestamps are timezone-aware ISO 8601 strings. `deadline_at` is later than
`issued_at`. The Agent MUST NOT begin a command after its deadline and SHOULD
stop work that can safely be cancelled when the deadline expires. It returns
one `command.result` with the same `command_id`.

### `command.result_rejected`

```json
{
  "command_id": "33333333-3333-4333-8333-333333333333",
  "reason": "command_is_not_pending"
}
```

V1 defines only the literal reason `command_is_not_pending`.

### `protocol.error`

```json
{
  "code": "invalid_message",
  "detail": "Message does not match the device protocol"
}
```

V1 defines `device_hello_required` and `invalid_message`. Core closes with
`4400` immediately after this message.

## Close codes

| Code | Meaning |
| ---: | --- |
| `1001` | Core is shutting down |
| `1003` | A binary/non-text frame was sent |
| `1009` | A message exceeded `max_message_bytes` |
| `1011` | Internal gateway failure |
| `4400` | Invalid V1 message, session, replay, or state transition |
| `4403` | An already accepted device session was revoked |
| `4408` | Initial hello or heartbeat timed out |
| `4409` | A newer connection replaced this device session |

Normal peer-initiated closure may use standard WebSocket code `1000`. Close
reason text is diagnostic only and MUST NOT be parsed as a stable API.

## Frozen capability and action IDs

The following identifiers are the complete Core V1 allowlist:

| Capability | Actions |
| --- | --- |
| `open_app` | `open` |
| `files` | `list`, `read`, `write` |
| `system` | `get_info`, `get_status` |

Core rejects an HTTP command whose capability/action pair is not registered or
whose capability is not effective for the live session. Core never emits a raw
shell action.

### Remaining Agent V1 blocker: action payload policies

The transport currently validates that `arguments` is a JSON object and that
`output` is JSON, but Core does **not** yet validate a field-level schema for
each action. The existing end-to-end profile exercises only:

```json
{
  "capability": "open_app",
  "action": "open",
  "arguments": {"name": "PyCharm"},
  "successful_output": {"opened": "PyCharm"}
}
```

Until per-action argument and result schemas are agreed and tested, their
semantics are not frozen by this document. This is a remaining V1 blocker, not
permission for an Agent to accept arbitrary input. An Agent implementation
MUST default-deny unrecognized argument shapes, resolve applications through a
local application allowlist, constrain file operations to configured roots,
canonicalize and re-check paths, and implement system actions through explicit
read-only adapters. It MUST NOT concatenate protocol values into a shell
command. The `files` and `system` actions SHOULD remain disabled in an Agent
release until those schemas and policies are frozen.

## Compatibility discipline

Bug fixes that preserve every documented wire shape and meaning MAY ship under
V1. A change that would make an existing valid V1 message invalid, make an
existing invalid/unknown field valid, introduce another message or action, or
alter ordering/state semantics requires a new protocol version. Core's golden
contract tests are intended to fail when such drift occurs.
